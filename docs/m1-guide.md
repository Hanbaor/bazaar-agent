# M1 采购 Agent 实作指南

M1 的目标是跑通一局采购：读取委托，创建市场，模型调用工具调查和下单，服务端记录订单与账本，独立验收，页面展示过程并能触发断货。完成时记录真实模型的 token 用量和单局费用或明确标注的费用估算。

当前已经实现委托和场景校验、三个开发场景，以及市场初始化、搜索、公开查询和库存修改。用户已在本地运行通过 33 个测试。报价、统一动作执行、交易持久化、HTTP/MCP 接口、Agent 循环和页面仍需要按下文实现。本文提供全阶段的实现任务、接口约定、参考片段和验收方法；其中的未来模块需要由你创建，不能把参考片段当成已经存在的完整程序。

以下项目路径均相对仓库根目录。你的 WSL 根目录是 `/mnt/d/bazaar-agent`，Windows 对应 `D:\bazaar-agent`。

## 3 批次 A 报价和议价

### 数据和文件

新增 `market/sim/quotes.py`，区分三种数据：买方提出的出价、卖家接受后生成的报价单、一次出价的处理结果。

```python
# 这个文件只定义报价数据。市场负责决定是否接受，交易服务负责真正下单。
from typing import Literal

from pydantic import BaseModel, ConfigDict, Field


class OfferRequest(BaseModel):
    # 任务和动作身份由执行程序管理，不放进模型生成的业务参数。
    model_config = ConfigDict(extra="forbid")

    listing_id: str = Field(min_length=1)
    unit_price: int = Field(ge=0, strict=True)  # 买方愿意支付的单价，单位为分。
    qty: int = Field(gt=0, strict=True)


class Quote(BaseModel):
    # 这是服务端生成的确定报价，客户端提供的任意对象不能代替此记录。
    model_config = ConfigDict(extra="forbid")

    quote_id: str = Field(min_length=1)
    task_id: str = Field(min_length=1)
    listing_id: str = Field(min_length=1)
    listing_version: int = Field(ge=1, strict=True)
    unit_price: int = Field(ge=0, strict=True)
    qty: int = Field(gt=0, strict=True)
    created_at: int = Field(ge=0, strict=True)
    expires_at: int = Field(ge=0, strict=True)


class OfferResult(BaseModel):
    # 返回后由调用者按 status 决定继续调查、接受报价或换方案。
    model_config = ConfigDict(extra="forbid")

    status: Literal["accepted", "counter_offer", "rejected"]
    quote: Quote | None = None
    counter_price: int | None = Field(default=None, ge=0, strict=True)
    error_code: str | None = None
```

这里的 `accepted` 表示卖家愿意按报价单出售，库存和资金尚未扣减。`counter_offer` 返回卖家本轮公开报价；`rejected` 可以表达库存不足等业务拒绝。它们是出价结果，后面的工具执行层还会统一包装成功、终局拒绝、等待授权、结果未知四类执行结果。

### 扩展策略配置

在 `Listing` 中增加 `concession_step`，类型为非负整数，默认 0，单位是“分／轮”。它是内部策略参数，不加入公开字段白名单。

在 `MarketTemplate` 中增加：

- `pricing_mode`：`fixed` 或 `concession`，默认 `fixed`。
- `quote_ttl_min`：报价有效时长，正整数，默认 30 个模拟分钟；与审批有效期分别管理。

原来的固定价模板保持四个挂牌的价格不变。新增 `negotiation_demo_v1.json` 作为议价测试模板，复制原模板后修改模板标识、设置 `pricing_mode=concession`，并把 `lamp_a` 改为标价 15000、底价 12000、每轮让步 1000。其余挂牌保留原配置。

同步扩展 `Scenario.market` 和 `MarketTemplate.template_id` 的允许模板名，使测试能选中这个新模板。新模板继续沿用现有四个挂牌编号。

目前构造函数中的“底价必须等于标价”要改为按策略检查：所有挂牌的底价不得超过标价；固定价模板还要求底价等于标价、让步金额为 0。固定价模板不能被配置成会降价的策略。

### 实现出价处理

在 `MarketSimulator.__init__` 增加自己的报价表、报价序号、议价轮次字典和报价有效时长。议价轮次以 `(task_id, listing_id)` 为键，防止两个任务互相使用对方的议价进度。

`make_offer(task_id, request)` 按以下顺序处理：

1. 检查受信任的任务上下文，查找挂牌。
2. 数量超过库存时返回 `rejected / OUT_OF_STOCK`。
3. 当前任务对当前挂牌进入新一轮议价。
4. 计算卖家本轮要价 `max(reserve_price, list_price - concession_step * round_number)`，第一轮的轮次为 1。
5. 买方出价低于本轮要价，返回 `counter_offer`，不创建报价单。
6. 买方出价达到本轮要价，按本轮要价创建报价单，不能因为买方愿意多付就改变固定价。
7. 保存报价单的独立副本，再把本次结果返回给调用者。

报价编号由程序生成。在内存模拟器中可用局内递增序号；数据库阶段使用适合持久化的编号与唯一约束。不得把场景编号当作采购任务编号。

增加 `get_quote(task_id, quote_id)`：先检查报价是否属于当前任务，再返回副本；不存在或属于其他任务都返回 `NOT_FOUND`。调用者修改收到的报价，不能改变服务端持有的原始报价。

再增加 `get_policy(seller_id, topic)`。固定价模板的 `pricing` 主题返回“固定价格，不议价”以及证据编号。未知卖家或主题返回 `NOT_FOUND`，不能在政策结果中导出隐藏底价。

这一批的业务方法是内部逻辑。直接调用代表一次新尝试，时间消耗与重试识别由下一批的统一入口负责。

### 报价测试

新增 `tests/test_quotes.py`，验证：

- S01 台灯出价 12000 时生成单价 12000、数量 1 的报价，库存仍为 1。
- 固定价台灯出价 13000，报价仍为 12000；出价 10000 时收到还价 12000。
- 台灯库存只有 1，需求 2 时拒绝。

## 4 批次 B 动作、时间和事件

### 统一执行入口

新增 `market/sim/actions.py`，或在引擎中建立清晰的执行入口。约定形式：

```text
run_action(context, action_id, tool_name, arguments)
```

`context` 表示执行程序已经确定的任务和实例身份；模型只生成业务参数。调用流程是“校验身份和参数 → 查重复 → 新动作推进时间 → 执行业务 → 保存结果”。现有搜索等内部方法保持纯查询，不能再各自推进一次时钟。

先使用以下耗时：搜索 1 分钟、查看挂牌 1 分钟、查询政策 1 分钟、询问卖家 5 分钟、出价 5 分钟。恢复查询 `get_operation` 和 `list_task_orders` 不推进时钟。事件作为动作的一部分生效，不另收一次时间。

内存阶段用 `(task_id, action_id)` 保存请求和结果。相同编号、相同规范化参数返回原结果，不重新计时、议价或生成报价；相同编号换参数则拒绝。保存与返回都使用独立副本，防止调用者篡改缓存。

业务摘要覆盖工具名和稳定业务参数。后面的执行代次、认证信息和审批凭据单独校验，不能把变化的认证信息混进业务动作摘要，否则同一操作恢复或补上审批时会被误判为不同请求。读取缓存结果前仍需检查任务归属。

内存缓存只在当前进程内有效。M1.3 把需要保存的结果放进数据库；跨进程故障恢复在 M2 完整验证。

### 模拟时间和报价校验

报价使用动作生效时的模拟时刻。例如从 540 开始，新出价消耗 5 分钟，则报价创建于 545，30 分钟后在 575 失效。有效条件是 `sim_time < expires_at`，等于失效时刻也算过期。

增加内部 `validate_quote`，检查任务归属、请求数量、挂牌版本和有效期。报价有效不能证明库存足够；下单事务还要重新检查库存、预算和清单剩余数量。

增加修改价格或条款的内部入口：值实际变化时递增挂牌版本。固定价模板改价时保持其固定价策略一致。单纯库存变化不递增价格和条款版本，因此 S02 最终应得到库存不足错误。

### 自动触发断货

初始化市场时复制 `scenario.events`，并建立本局已触发事件编号集合。每次成功创建新报价单后，查找匹配的 `after_quote_created` 事件，把目标库存设为 0 并记录事件编号。

事件在一局中只生效一次。还价、拒绝、重复动作和其他挂牌的报价不触发它。库存之后被管理员恢复时，同一个事件也不能再次清空库存。

固定价模板不人为添加随机价格。如果后续需要随机回复或扰动，使用每个实例独立的随机数生成器，例如 `random.Random(seed)`，不能共用一个全局随机状态。

### M1.2 验收

- 原有 33 个测试继续通过。
- 新动作计时正确，同编号重试不改变时刻、轮次、报价数量和事件记录。
- S02 的 `lamp_a` 生成报价后自动变为库存 0，报价记录仍存在。
- 不同实例各自触发事件，重复请求不重触发。
- 过期报价、版本变化和跨任务报价被拒绝。
- 同配置、种子和动作序列得到相同的业务结果。

此时先提交和合并 M1.2，再开始数据库交易层。

## 5 批次 C PostgreSQL 下单事务

### 从内存模块转向持久化服务

新增 `market/ledger/db.py`、`market/ledger/models.py`、`market/ledger/service.py` 和 `market/judge.py`。初始化脚本放在 `scripts/init_db.py`，通过 `python -m scripts.init_db` 从项目根目录执行。

这四个文件分别解决四个问题：`db.py` 管理连接与会话，`models.py` 描述数据表，`service.py` 实现业务事务，`judge.py` 核对真实成交结果。Pydantic 模型负责接口数据是否合法，SQLAlchemy 模型负责数据如何落表；两者不能相互代替。

数据库会话 `Session` 代表一次与数据库交互的工作单元。不要给整个 Web 服务共用一个可变会话；每次业务请求创建自己的会话，在一次事务内完成相关检查和写入，然后关闭。数据库连接池可以共用。

从这一批开始，市场服务实际使用的库存、时钟、报价、订单、动作结果和账本以 PostgreSQL 为事实来源。内存模板用于初始化，模拟器中的策略函数用于计算；HTTP 服务不能一边从内存读库存、一边只在数据库扣库存。写入后也不能再用旧模板覆盖当前库存。

最低需要以下表；具体字段按总计划和规格细化：

| 表 | 保存什么 | 关键约束 |
| --- | --- | --- |
| market_instances | 初始配置、种子、模拟时刻、下一个事件序号 | 每局独立，时间非负 |
| sellers、products | 卖家、公开规格描述、内部策略和商品真值 | 按实例隔离，隐藏数据由服务端读取 |
| listings | 卖家商品关系、价格、底价、库存、发货时长、版本 | 库存和金额非负，版本正数 |
| tasks、mandates | 任务状态、已花金额、所有者、当前委托版本及委托内容 | 用户修改委托必须生成新版本 |
| quotes | 任务、挂牌版本、单价、数量、创建与失效时刻、使用状态 | 任务作用域明确，报价由服务端生成 |
| actions | 任务与动作编号、业务摘要、确定结果 | `(task_id, action_id)` 唯一 |
| orders | 操作号、清单项、报价单、数量、单价、金额、承诺送达时刻 | 操作号唯一，订单关联有效任务和清单项 |
| ledger_entries | 订单扣款、扣款后的已花金额 | 每张订单一条扣款，只追加 |
| events | 实例、序号、事件类型和公开载荷 | `(instance_id, seq)` 唯一 |

字段设计至少明确以下关联，避免后面只靠字符串拼接猜测归属：

- `listings` 带 `instance_id`，同一模板的 `lamp_a` 在不同实例中是不同的数据库记录。可用独立主键，并对 `(instance_id, listing_id)` 建唯一约束。
- `tasks` 带 `instance_id`、`owner_id`、`current_mandate_version`、`spent` 和状态；`mandates` 按 `(task_id, version)` 保存不可变版本。
- `quotes` 带 `task_id`、挂牌关联、数量、单价、挂牌版本、创建与失效时刻，以及是否已使用。
- `orders` 带 `task_id`、`item_id`、`op_id`、报价关联、数量、单价、总额与承诺送达时刻；总额必须等于单价乘数量。
- `ledger_entries` 带订单关联、任务关联、扣款额和扣款后已花金额；订单关联唯一，防止一张订单记两次账。
- `actions` 保存工具名称、稳定业务摘要、执行状态和公开结果；`events` 保存递增序号及经过白名单筛选的公开载荷。

外键解决“引用的记录必须存在”，检查约束解决“单条记录的金额、数量等基本合法”，事务中的业务检查解决“当前预算、库存、累计购买量一起满足要求”。例如数据库不知道用户这次要买几根数据线，所以累计数量仍需读取委托并在任务锁内检查。

持久化阶段由执行程序生成全局唯一操作号，例如 UUID。测试中也要避免不同任务复用同一个全局订单操作号。任务令牌只记录必要的校验信息，不能写进公开事件或模型上下文。

### 你要亲手写的下单事务

事务是一组必须一起成功的写入。SQLAlchemy 的事务上下文在成功时提交、异常时回滚；`with_for_update()` 用于请求数据库行锁。[事务说明](https://docs.sqlalchemy.org/en/21/orm/session_transaction.html)、[行锁接口](https://docs.sqlalchemy.org/en/21/core/selectable.html#sqlalchemy.sql.expression.Select.with_for_update)

下面是执行顺序示意。各个查询和写入辅助函数需要按已定义的表实现，不能把这段直接当作完整服务文件运行：

```text
校验调用者和任务作用域
计算稳定的业务请求摘要

开始事务
    按统一顺序锁实例、任务、报价和挂牌
    再次检查任务状态、委托版本和执行上下文

    若当前操作已有确定结果：
        检查摘要是否一致
        返回原结果，不再次扣款或推进时钟

    读取当前委托、报价、库存和清单累计购买数量
    检查报价属于本任务，数量匹配，版本有效，尚未过期且未使用
    检查清单项属于委托，累计数量不超需求，库存足够
    检查动作生效时刻和卖家承诺送达时刻
    检查原预算以及本笔操作绑定的有效批准

    若有确定业务拒绝：
        保存拒绝结果和必要事件，然后正常提交事务
    否则：
        扣库存、创建订单、增加任务已花金额
        标记报价使用状态、追加账本、保存动作结果和事件
提交事务

返回确定结果
```

固定锁顺序，避免不同入口以相反顺序取锁。锁任务行用于防止两个请求同时认为预算和需求数量足够；库存也需要在锁定挂牌后检查。实例行负责统一时钟和事件序号。多条挂牌需要锁定时采用稳定的编号顺序。

确定的业务拒绝需要作为正常分支提交其动作结果；如果先写拒绝记录再抛出异常让整个事务回滚，重试就无法复用这份结果。数据库异常则回滚全部相关写入，不能留下半张订单或没有订单的扣款。

M1 的三个场景都可以在原预算内采购或正确停止。超预算时先返回需要审批并停止，保持拒绝执行；完整的审批绑定、等待与恢复在 M2 完成。审批比例不是可以直接消费的额外额度。等待授权也不能被缓存为永久的终局拒绝。

### 第一版独立验收

验收程序从订单、账本和场景真值计算实际结果，再与 Agent 报告核对：

- 清单项是否都买齐，累计数量是否恰当。
- 每张订单是否来自有效授权和有效报价。
- 是否买到违反必须项的商品，例如二手或翻新。
- 订单总额、账本累加和任务已花金额是否一致。
- 结果属于原授权内完成、经审批完成、正确停止、部分停止、失败还是违规。

模型报告中的“完成”只是声明；`expected.outcome` 也只是场景目标。二者都不能代替账本和真值。对于 S03，空订单本身不能证明正确停止，需要结合公开固定价、候选范围和最低整套成本核对停止依据。

### 数据库测试

新增 `tests/test_orders.py`、`tests/test_concurrency.py`、`tests/test_judge.py`。使用独立测试数据或数据库清理夹具，避免测试污染个人开发任务。

必须验证正常扣款、超预算拒绝、超数量拒绝、无库存拒绝、过期和版本变化拒绝、同操作号重复提交只产生一笔订单与扣款、同编号不同内容拒绝、事务失败全部回滚。再用两个独立数据库会话同时购买最后一件库存，确认只允许一笔成交；同任务的两个请求也不能一起突破预算或清单数量。

一个便于理解的并发案例：库存只有 1，请求甲和乙都想买 1。如果各自先读到库存 1，再分别扣款，就可能卖出两件。行锁让乙等待甲提交；乙取得锁后必须重新读取当前库存，看到 0 后拒绝。任务锁同理，保护的是同一个任务的预算和累计购买量。测试必须真的使用两个会话，连续调用同一个函数两次只能验证顺序行为。

### 参考轨迹重放：在 Agent 之前证明市场闭环正确

新增 `scripts/replay_reference.py`，提供 `--scenario` 参数。它是测试执行器，可以读取完整场景，但所有采购操作必须走同一套服务接口。这个脚本不用模型，不应产生模型费用。

执行顺序如下：

1. 加载场景，创建独立市场实例及采购任务，保存任务身份上下文。
2. 对每个参考步骤，调用公开挂牌查询，按公开固定价调用 `make_offer`。
3. 从实际结果取得报价编号，以新的下单操作号调用 `place_order`，不能自己编造报价对象。
4. 对照该步骤的 `expected_result`：成功必须确实有订单，断货必须是 `OUT_OF_STOCK`，并且没有扣款。
5. 最后从实际订单和账本计算总花费，调用独立验收，再与场景的参考目标核对。

S03 的参考步骤为空，仍要执行公开调查：枚举候选、查看规格与固定价政策，记录最低整套价格和停止依据，然后提交停止报告。不能因为参考步骤为空就直接把场景标为通过。这个固定模板的最低整套成本计算只用于重放和核对；真实 Agent 自己根据公开观察决定采购方案。

脚本还应输出任务编号、实例编号、每步状态、订单总额和验收结果，便于排查。以后实现 HTTP 后，把执行器切换成 HTTP 客户端，继续使用同一组参考场景。

### 先让 HTTP 服务可用

提供任务创建、进度查询、工具调用、报告提交与验收、市场干预和事件读取接口。请求体使用 Pydantic 模型并禁止未知字段；FastAPI 会读取并验证这些模型。[请求体说明](https://fastapi.tiangolo.com/tutorial/body/)

先固定一组路由，之后 Agent 和页面都调用它们：

| 方法与路径 | 作用 | 需要注意 |
| --- | --- | --- |
| `POST /tasks` | 选择开发场景，创建实例和任务，返回任务编号及本地任务令牌 | 返回给客户端的是公开委托和任务信息，不能返回完整场景 |
| `GET /tasks/{task_id}` | 读取公开委托、当前状态、模拟时刻和已花金额 | 校验令牌的任务归属 |
| `POST /tasks/{task_id}/actions` | 请求体包含动作编号、工具名称和业务参数 | 分派到唯一业务服务，不能动态执行任意函数名 |
| `GET /tasks/{task_id}/operations/{action_id}` | 核对原动作是否已经提交 | 只查询，不推进时钟 |
| `GET /tasks/{task_id}/orders` | 查看本任务订单与账本 | 只查询，不推进时钟 |
| `POST /tasks/{task_id}/finish` | 保存结构化报告并执行独立验收 | 服务端确定最终状态 |
| `POST /tasks/{task_id}/interventions/stockout` | 页面手动触发指定挂牌断货 | 本地演示权限与普通 Agent 工具分开 |
| `GET /tasks/{task_id}/events` | 按事件序号发送公开 SSE 流 | 需要同样的任务鉴权 |

各个工具的业务参数按 `docs/spec.md` 第 4 节实现。`ask_seller` 使用确定性的卖家回复模板，返回回复与证据编号，不能通过问卖家读到隐藏底价。M1 的 `request_approval` 明确返回需要审批并停止执行，完整审批交互属于 M2；不能自动批准，也不能把 20% 申请上限当余额。

工具调用的业务参数只包含挂牌、价格、数量等。调用者身份和任务归属由服务端认证上下文得到；动作编号由执行程序分配。不能从模型参数中信任用户号、任务号、审批状态或执行代次。

本地开发至少使用任务作用域令牌，保证一个任务的客户端不能操作另一个任务。M4 再接线上邀请码和账户保护。API key 只存在于后端环境变量。

执行层统一使用如下形状表达工具结果：

```json
{
  "status": "success",
  "data": {},
  "error": null
}
```

其他状态为 `rejected`、`approval_required`、`unknown`。错误部分包含稳定错误码和可理解的说明。`counter_offer` 是一次成功执行的业务结果，放进 `data`，不能与网络层的结果未知混淆。

HTTP 请求超时后，客户端使用原动作编号查询 `get_operation`，查到结果就采用；尚未查到也继续沿用原编号。只有确认要换一笔业务方案时才分配新操作号。不能每次网络重试都生成新 UUID。

HTTP 服务只调用业务服务，不能再写第二份预算检查或库存扣减逻辑。SSE 和普通接口同样需要任务或实例访问权限；所有公开事件使用安全的字段白名单。

## 7 批次 E 模型适配和纯 Python Agent

### 先统一模型接口

模型适配层继续使用已经连接成功的 Qwen 模型、兼容接口地址和环境变量。供应商的工具调用能力需要由你手动验证；OpenAI Docs 解释 SDK 消息协议，并不替代第三方服务的兼容性验证。

把真实 SDK 回复转换成自己的内部结构，例如：

```text
ModelTurn
  content：可选文本
  tool_calls：函数调用列表，每项含 id、function.name、function.arguments

```

`FakeModel` 实现相同接口，在测试中返回你预设的工具调用，不能访问真实模型。这样先验证循环，再由你手动执行真实调用。

### 工具定义和上下文

工具参数模型生成 JSON Schema，里面只包含模型可以决定的业务字段。初版使用普通函数工具格式，服务端仍做完整 Pydantic 校验；不要假设供应商一定支持某种严格 schema 模式。

初始上下文包含用户委托、采购规则和工具说明。商品描述、政策和卖家消息标记为外部内容，不能修改授权。场景预期、参考轨迹、未来事件、隐藏真值和密钥不放进提示词。

区分三个编号：`task_id` 来自任务服务，`tool_call_id` 来自模型回复并用于关联对话消息，`action_id/op_id` 是执行程序分配并稳定重用的业务操作号。模型回复中的新调用编号不能直接代替待查证业务操作的原编号。

### 循环的执行顺序

你亲手编写的 `run_agent` 按下面的结构实现。这里是跨模块算法说明，适配器、执行器和报告模型需要按本章约定实现：

```text
读取任务和当前合法委托
读取本任务已经存在的订单，建立剩余采购清单
创建系统规则与用户委托消息

在模型轮数、工具动作数、模拟时间和费用允许的范围内循环：
    调用模型适配器，累计 usage 并记录模型和调用耗时
    保存 assistant 消息，包括模型提出的 tool_calls

    没有工具调用时：
        不能仅凭自然语言“完成”判定成功
        按协议要求结构化结束；重复无进展时停止

    依次处理每个工具调用：
        解析 arguments，并按该工具的参数模型校验
        若名字或参数错误，返回可修正的工具错误
        若是 finish，校验报告并结束，不执行同一批后续采购
        否则由执行程序分配动作号，调用受信任的工具执行器
        执行器处理网络重试和结果查证，保留原动作号
        结果未知或需要审批时安全停止或等待，不能另下同一笔新单
        把执行结果作为 role=tool 消息写回，关联原 tool_call_id

    连续三次相同调用且业务观察无变化时，按无进展停止

提交结构化报告并调用独立验收
返回实际结果、轨迹、用量和费用记录
```

观察变化的比较应排除临时动作号和普通时间戳，关注库存、价格、版本、订单和剩余需求等业务信息。控制模型轮数和工具动作数，防止一次回复包含很多调用时绕过上限。已进入停止状态后，为本批剩余调用记录“未执行”，不能继续下单。

下面的代码示意正确的消息关联方式；`execute_tool` 是前文实现的受信任执行器。实际循环还需要实现上面的限制、校验和停止分支：

```python
# JSON 用来解析工具参数，并把工具结果转成模型消息中的文本。
import json


# 一轮模型回复可能包含多个工具调用，先把整条 assistant 消息放进历史。
message = response.choices[0].message
messages.append(message.model_dump(exclude_none=True))

for call in message.tool_calls or []:
    # 这里只接受已经注册的函数工具。其他类型由适配器明确处理。
    if call.type != "function":
        raise ValueError("不支持的工具调用类型")

    # arguments 是 JSON 字符串。实际实现要捕获解析与参数校验错误。
    arguments = json.loads(call.function.arguments)

    # execute_tool 管理业务身份、稳定操作号、超时查证和服务端调用。
    # 它返回可 JSON 序列化的公开结果，不能返回 ORM 对象或隐藏真值。
    result = execute_tool(call.function.name, arguments)

    # tool_call_id 关联的是这轮对话调用，不等于执行器管理的业务操作号。
    messages.append(
        {
            "role": "tool",
            "tool_call_id": call.id,
            "content": json.dumps(result, ensure_ascii=False),
        }
    )
```

这种 assistant/tool 消息配对来自 [OpenAI Docs 工具调用说明](https://developers.openai.com/api/docs/guides/function-calling)。先用假模型测试消息顺序及多工具回复，再手动验证所选兼容服务的实际行为。

### 报告与费用

报告包含模型声明的状态、订单编号、完成项、停止原因和证据编号。验收器使用实际状态判断，不能直接采用模型声明。

每次模型调用记录模型标识、输入/输出 token、耗时和错误码。价格由配置提供，费用按供应商适用的计费规则计算并注明估算口径；价格未配置时记为未知，不能记成 0。实际账单与估算存在差异时分开报告。

## 8 批次 F 页面与演示

新增 `web/index.html`、`web/app.js`、`web/style.css`，由 FastAPI 提供静态文件。页面先提供选择场景、发委托、显示采购状态、订单、账本、事件和一个断货按钮。

FastAPI 可以用流式响应发送数据，事件帧必须按 SSE 格式组织。[流式响应说明](https://fastapi.tiangolo.com/advanced/custom-response/#streamingresponse)

演示手动断货时，在“已取得台灯报价、尚未下单”的位置设置一个明确的演示暂停点。页面显示暂停原因后，你点断货再继续执行，Agent 才能稳定观察到失败并改选。这个暂停点只用于演示，不能改变实际下单检查，也不能把事先写好的替代方案塞进模型上下文。

在 `docs/notes/m1.md` 记录一次正常采购、一次断货改选和一次预算不足停止。每个案例包含任务编号、关键公开观察、调用顺序、实际订单与花费、模型报告、验收结论，以及你理解的原因。再记录一次两会话竞争库存的测试结果，解释为什么只有一个请求成功。

## 9 M1 最终验收清单

- [ ] 所有自动化测试在 PostgreSQL 上通过，CI 使用独立测试数据库和假模型。
- [ ] 一条命令能创建实例并通过参考步骤完成三件套场景，订单和账本验收一致。
- [ ] S02 自动断货和页面手动断货都能复现，失败尝试不会扣款，合法替代方案能够完成。
- [ ] S03 能基于公开证据说明预算不足，正确停止；部分成交时如实报告部分停止。
- [ ] 一个真实模型采购 Agent 能经由工具完成一局，保留完整公开轨迹和独立验收结果。
- [ ] HTTP 与 MCP 复用同一套市场和交易规则，MCP Inspector 完成握手、列工具、调用工具。
- [ ] 记录单局 token、模型、费用或明确口径的估算，以及模拟时间和工具动作数。
- [ ] 页面能看到过程、订单、账本和断货事件。
- [ ] 你能解释预算与数量为什么需要事务锁、报价为什么不等于成交、模型报告为什么需要独立验收。
- [ ] 分支已通过 PR 合并到主分支，阶段小结写明实现、测试、已知限制和 M2 工作。

M1 做到这里才叫“一单跑通”。M2 再重点处理持久化状态图、逐笔审批、执行代次和故障恢复，不能因为正常场景跑通就宣称已经完成可靠性验证。

## 10 以后的代码注释要求

仓库根目录 `AGENTS.md` 已记录持续采用的教学与注释约定。每份新代码说明模块作用，重要函数解释输入输出和执行顺序，金额、时间和身份字段注明单位与来源。

事务、权限、去重、状态复制、异常处理和模型消息协议都要说明为什么这样写。注释对应当前行为，尚未实现的步骤明确保留在任务和接口约定中，不能用注释冒充功能实现。
