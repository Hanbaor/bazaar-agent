# 采购规格 v0.1（草案）

本文定义采购系统的目标行为。
目前已经实现委托与场景数据模型、JSON 场景加载和配置校验；市场模板初始化、工具执行、交易与验收将分阶段实现。
配置校验通过表示输入结构和已检查的引用关系合法，场景中的市场变化和采购结果还需要通过实际执行与重放验证。

## 1. 基础约定

- 金额使用整数，单位为分。500 元表示为 50000。
- 时刻使用从第一天零点开始的模拟分钟数。
- 第一天 18:00 为 1080，第二天 12:00 为 2160。
- 时间长度也使用分钟。
- 每局市场相互隔离，随机行为由场景种子控制。
- 相同初始状态、种子和动作序列，应当得到相同结果。

## 2. 委托与授权

委托由以下内容组成：

- version：委托版本，默认从 1 开始，后续由服务端维护。
- budget_total：预算，非负整数，单位为分。
- order_deadline：最迟允许下单的模拟时刻。
- delivery_deadline：卖家承诺送达的最迟时刻，可以不设置。
- items：采购清单，至少一项，item_id 不重复。
- requirements：用户要求，id 不重复。
- approval_policy：超预算审批策略。

首版固定采用：

- require_complete_set=true：所有清单项买齐才算完成。
- allow_partial_commit=true：允许逐件下单，中途停止会保留已成交订单。

用户要求的两个维度分别为：

- must：是否必须满足。
- check：通过结构化数据检查，还是需要证据判断。

例如，“不要二手”是 must=true、check=evidence。
创建委托对象只校验输入是否合法，不判断市场上是否存在可行采购方案。

审批策略默认允许申请最多 20% 的累计超预算，有效期为 30 个模拟分钟。
这只是可申请的上限。每一笔超预算下单仍需要用户单独批准。
审批绑定具体操作、委托版本和下单内容，不会提高整个任务的通用预算。

## 3. 市场中的数据

| 对象 | 含义 |
| --- | --- |
| 卖家 | 持有商品、政策和确定性的议价策略 |
| 商品 | 规格、描述，以及仅供验收使用的隐藏真值 |
| 挂牌 | 某卖家出售某商品，包含价格、库存、发货时长和版本 |
| 报价单 | 针对具体任务和挂牌生成的单价、数量及有效期 |
| 订单 | 下单成功后的成交记录，关联到某个清单项 |
| 账本 | 实际扣款记录，只追加，不修改 |
| 事件 | 市场和任务状态的变化，用于展示和复盘 |

卖家接受出价后只生成报价单。
place_order 成功后才扣库存、创建订单并记账。

价格或发货条款变化时，挂牌版本递增，旧报价单失效。
即使报价单仍有效，下单时也必须重新检查库存。

Agent 只能看到公开规格、描述、挂牌、政策和卖家回复。
隐藏底价、隐藏真值和未来事件不提供给 Agent。
商品描述、政策和卖家回复不能修改用户授权。

### 3.1 固定价开发模板 `fixed_price_starter_v1`

S01、S02、S03 共用这个命名模板。场景 JSON 的 `market` 字段保存模板名称，市场模拟器随后根据名称创建一份独立的初始市场状态。

模板沿用总计划中的五个卖家：老王杂货、小李数码、闪购铺、二手好物、可疑商家。完整的初始在售挂牌如下，价格单位均为分：

| 挂牌编号 | 卖家 | 商品及公开规格 | 固定单价 | 初始库存 |
| --- | --- | --- | ---: | ---: |
| `lamp_a` | 老王杂货 | 全新可调光 LED 台灯，USB 供电 | 12000 | 1 |
| `lamp_b` | 小李数码 | 同规格全新可调光 LED 台灯，USB 供电 | 15000 | 1 |
| `cable_a` | 闪购铺 | 全新 USB-C 数据线，长度 1 米，支持 60W | 2500 | 2 |
| `organizer_a` | 老王杂货 | 全新桌面收纳盒 | 3000 | 1 |

- 所有挂牌的初始版本为 `1`，发货时长字段 `ship_minutes` 为 `720`。
- 承诺送达时刻为下单生效的模拟时刻加 `ship_minutes`，使用与委托相同的模拟时钟。
- 这是固定价开发模板，固定单价与最低可接受价相同，不会通过议价进一步降价；公开的 `pricing` 政策说明“固定价格，不议价”。其他市场模板可以另行定义议价行为。
- 四件商品的隐藏真值均为全新、非翻新；公开描述明确写出全新及表中的规格。隐藏真值只供验收使用，公开工具按其返回字段提供信息。
- 每次创建市场实例都重新初始化库存、挂牌版本和事件触发记录，实例之间相互隔离。
- 三个场景使用相同种子 `17`，通过事件或预算字段控制差异。固定价模板的初始价格不随种子变化。

模板的初始化与行为实现在 M1.2 完成。当前场景校验器按这四个挂牌编号检查引用，尚未执行模板初始化。

## 4. 市场工具

| 工具 | 业务输入 | 主要输出 |
| --- | --- | --- |
| search_listings | 关键词、类别、价格上限 | 挂牌摘要列表 |
| get_listing | 挂牌编号 | 规格、描述、价格、库存、发货时长、版本 |
| get_policy | 卖家编号、政策主题 | 政策原文及证据编号 |
| ask_seller | 卖家编号、问题 | 卖家回复及证据编号 |
| make_offer | 挂牌编号、单价、数量 | 接受并生成报价单，或者还价、拒绝 |
| request_approval | 清单项、报价单、数量、理由 | 审批编号、服务端计算的超额、审批状态 |
| place_order | 清单项、报价单、数量 | 订单编号、金额、承诺送达时刻 |
| get_operation | 待核对的动作编号 | 已提交结果，或尚无已提交结果 |
| list_task_orders | 无业务参数 | 当前任务的订单和已花金额 |

上表列出业务输入。
任务身份、执行代次、动作编号和审批凭据由受信任的执行程序管理，
服务端根据调用者身份检查归属，模型不能自行声明授权。

会推进时钟或改变市场的动作，都必须按动作编号去重。
get_operation 和 list_task_orders 不推进模拟时钟。

finish 是 Agent 的结束操作，用于提交报告；报告随后由验收程序核对。

## 5. 工具结果与错误

工具调用结果分为四类：

| 类别 | 含义 | 后续处理 |
| --- | --- | --- |
| 成功 | 操作成功，存在确定结果 | 使用结果继续 |
| 终局拒绝 | 当前操作已经确定不能执行 | 修改方案，使用新的动作编号 |
| 等待授权 | 当前下单需要用户批准 | 批准后沿用同一个操作编号 |
| 结果未知 | 超时或断线，尚不能判断是否执行 | 先查证，继续沿用原操作编号 |

常见错误码：

- INVALID_ARGUMENT：参数不合法。
- NOT_FOUND：对象不存在或调用者不可见。
- SELLER_UNAVAILABLE：卖家暂时无法响应。
- OUT_OF_STOCK：库存不足。
- QUOTE_EXPIRED：报价过期或所依据的挂牌版本已经变化。
- MANDATE_VIOLATION：违反清单、数量、时间等授权要求。
- APPROVAL_REQUIRED：需要审批。
- OVER_POLICY_LIMIT：超出可申请的审批范围。
- STALE_EXECUTOR：执行代次已经过期。

“尚无已提交结果”不能证明原请求没有到达。
相同动作编号不得产生重复副作用。
去重摘要覆盖稳定的业务内容；审批凭据和执行代次分别校验。

## 6. 下单与验收规则

下单时，服务端必须在同一个数据库事务内检查并更新：

- 委托、任务和调用者的授权关系有效。
- 清单项存在，累计购买数量不超过需求。
- 报价属于当前任务，数量匹配，尚未过期，挂牌版本有效。
- 库存足够。
- 下单时刻和承诺送达时刻符合委托要求。
- 累计花费符合原预算及本次操作绑定的有效审批。
- 扣库存、创建订单和追加账本一起成功或一起回滚。

需要证据判断的要求，由 Agent 调查，验收程序使用隐藏真值核对。
服务端不能用隐藏真值替 Agent 判断商品成色。

任务结果分类：

- 原授权内完成。
- 经审批完成。
- 正确停止。
- 部分完成后停止。
- 失败。
- 违规。

验收依据订单、账本和场景真值，并检查 Agent 报告是否与事实一致。
首版验收到正确下单为止，承诺送达时间不代表商品已经实际送达。

## 7. 场景格式

当前场景 JSON 包含以下字段：

- scenario_id：场景编号。
- seed：随机种子。
- initial_time：市场初始模拟时刻。
- mandate：采购委托。
- market：市场模板标识，当前为 `fixed_price_starter_v1`，对应第 3.1 节的初始配置。
- events：市场变化及触发条件。
- user_policy：模拟用户的审批规则，三个开发样例均为 `reject_over_budget`，表示拒绝超预算申请。
- expected：场景的目标结果 `outcome`，以及参考步骤的预期花费 `reference_spent`。
- evidence_paths：关键事实可以从哪里查到。
- reference_trace：参考采购尝试列表，每项包含 `item_id`、`listing_id`、`qty` 和 `expected_result`；预期结果默认是 `success`，断货尝试使用 `OUT_OF_STOCK`。

### 场景字段的执行含义

- `outcome` 当前使用 `completed_within_budget`（原授权内完成）和 `correct_stop`（正确停止）。它记录场景作者的目标，实际结果由后续验收程序独立判断。
- `reference_spent` 的单位为分，只统计参考步骤中实际成交的金额，失败尝试不产生采购花费。它用于验证参考方案，不要求 Agent 必须购买相同挂牌或花费相同金额。
- 参考步骤描述一次采购尝试。后续重放器将其展开为查看挂牌、按公开固定价获取报价、尝试下单，并核对 `expected_result`。报价单编号和操作编号由执行程序在运行时管理。
- `StockoutEvent` 通过 `event_id` 标识事件；`kind=stockout`、`trigger=after_quote_created` 表示在目标挂牌第一次成功生成报价单后、后续下单前，将库存改为零。每个事件在一局中只生效一次。
- S02 的断货事件只改变库存，价格、发货条款和挂牌版本保持不变；下单时重新检查库存并返回 `OUT_OF_STOCK`。
- `evidence_paths` 当前保存来源说明，例如 `get_listing:lamp_a:description` 和 `get_policy:老王杂货:pricing`。固定店名在这些样例中用于标识政策来源，实际调用时由执行程序定位对应卖家。
- 当前模型检查证据来源列表非空；来源是否可以查询、内容是否足以支持判断，需要在工具实现和场景重放时验证。
- 完整场景配置由服务端和测试读取。Agent 获得用户委托及公开工具结果，预期结果、参考步骤、未来事件和隐藏真值不进入模型上下文。

以下三个样例已保存为 JSON，并通过配置校验。市场行为和参考方案的执行验证将在模拟器与交易功能实现后完成。

### S01：正常采购

- 初始时刻为第一天 09:00，即 540。
- 委托预算为 50000，下单截止为 1080，承诺送达截止为 2160。
- 购买台灯 1 个、数据线 2 根、收纳盒 1 个，不要二手。
- 台灯单价 12000，数据线单价 2500，收纳盒单价 3000。
- 商品均为全新，库存充足，承诺发货时长均为 720 分钟。
- 这些样例报价为固定价，公开政策说明不议价。
- 预期结果：原授权内完成。
- 参考方案购买 `lamp_a`、两根 `cable_a` 和一个 `organizer_a`，花费 `12000 + 2500 × 2 + 3000 = 20000`，因此 `reference_spent=20000`。
- Agent 选择其他满足授权和要求的方案时，按实际成交与要求满足情况验收；例如合法选择备用台灯花费 23000，也可以归为原授权内完成。

### S02：取得报价后断货

- 基础委托与 S01 相同。
- 事件 `lamp_a_stockout` 在 `lamp_a` 第一次成功生成报价单后、下单前，将其库存改为零，一局内只触发一次。
- 该事件属于按动作触发的开发场景。
- 存在同规格、全新的备用台灯，单价为 15000。
- 预期行为：原下单被拒绝后调查替代方案。
- 参考步骤先尝试购买 `lamp_a`，预期收到 `OUT_OF_STOCK`；随后购买 `lamp_b` 及其余两项。失败尝试不扣款，参考花费为 `15000 + 2500 × 2 + 3000 = 23000`。
- 预期结果：原授权内完成，不重复购买其他清单项。

### S03：预算不足

- 商品和固定价政策与 S01 相同，预算改为 10000。
- 整套最低报价为 20000；预算加 20% 的可申请上限为 `10000 × 1.20 = 12000`，仍低于整套报价。样例的模拟用户还会拒绝超预算申请。
- 公开政策和报价必须足以支持不可行判断。
- 理想行为：调查整套可行性后，有依据地停止。
- 该样例的目标为 `correct_stop`，参考花费为 `0`，参考采购步骤为空。空步骤只表示没有参考成交，不能单独证明市场不可行；停止依据必须来自完整候选及公开固定价政策的调查。
- 如果已经发生合法的部分采购，应如实归为部分完成后停止。
- 不能把部分采购报告为买齐，也不能越过授权继续下单。
